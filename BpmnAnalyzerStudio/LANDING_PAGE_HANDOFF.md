# Контекст для бота: лендинг AnalystPad / BpmnAnalyzer Studio

## Задача следующего бота

Создать адаптивный статический сайт-лендинг для приложения и подготовить его к публикации на GitHub Pages. Лендинг — отдельная публичная презентационная страница, не замена редактору BPMN и не попытка встроить Desktop-приложение в GitHub Pages.

Перед началом проверь текущую структуру репозитория и существующие несохранённые изменения. Не перезаписывай пользовательские изменения и не включай `bin/`, `obj/` или другие артефакты сборки в сайт.

## Продукт

*   В интерфейсе веб-части приложение называется **AnalystPad**, подпись — «BPMN → ТЗ для аналитиков».
*   Название Desktop-окна — **BpmnAnalyzer Studio — Analyst Workspace**. Бренд пока не унифицирован; на лендинге лучше использовать **AnalystPad** как продуктовый бренд, а BpmnAnalyzer Studio упомянуть как название desktop-версии/проекта, если это нужно.
*   Это инструмент для бизнес- и системных аналитиков: моделировать бизнес-процесс в BPMN, проверять схему и использовать её как основу для черновика требований или технического задания.
*   Основной язык текущего интерфейса — русский. Сделай русский основным языком лендинга, если пользователь не задал иное.
*   Тон: ясный, профессиональный, практичный. Не обещай автоматическую генерацию «готового ТЗ» или ИИ-анализ: текущая генерация — локальное шаблонное преобразование данных BPMN.

## Фактически реализованные функции Desktop-приложения

Реализация находится в `src/BpmnAnalyzer.Desktop/Assets/Web/`.

1.  **BPMN-редактор на bpmn-js**
    *   Создание новой схемы; добавление BPMN-фигур через палитру редактора.
    *   Импорт `.bpmn`/`.xml` и сохранение схемы в BPMN XML.
    *   Масштабирование и вписывание схемы в область редактора.
    *   Редактирование названия выбранного элемента и описания для задач/событий; ID показывается только для чтения.
2.  **Проверка схемы**
    *   Проверяет число стартовых и конечных событий, подключения задач и шлюзов, названия задач и пулов, описание сервисных задач.
    *   Для исходящих веток Exclusive Gateway проверяет наличие условия или ветки по умолчанию.
    *   Проверяет простое структурное соответствие ветвления и слияния.
    *   Результаты показываются отдельным списком; при наличии ID элемента можно перейти к нему на схеме.
3.  **Черновики документов**
    *   По текущей схеме формируется текст одного из типов: техническое задание, список требований или свободные заметки.
    *   Пользователь может редактировать текст, копировать его и скачать как Markdown.
    *   Текст формируется простыми шаблонами по объектам схемы, не ИИ.
4.  **Проекты и локальное хранение**
    *   Проекты сохраняют BPMN XML и связанные текстовые документы в локальном хранилище браузера (IndexedDB; предусмотрен fallback на localStorage).
    *   Есть открытие/создание проектов, сохранение документов в проект, импорт и экспорт JSON-резервной копии.
    *   Хранилище локальное для текущего браузера/устройства: синхронизации, аккаунтов и серверного хранения нет.
5.  **Экспорт и демонстрация**
    *   Экспорт схемы в SVG и PNG.
    *   Простая анимация маркера по первой доступной ветви процесса.

## Важные ограничения и точность обещаний

*   Не называй продукт SaaS, облачной платформой или совместным редактором: таких функций в текущем коде нет.
*   Не обещай автоматическую публикацию, совместное редактирование, вход по аккаунту, серверное хранение, мобильное приложение, генерацию DOCX/PDF или ИИ-возможности: их реализация не подтверждена.
*   Утверждения о правилах валидации сверяй с `src/BpmnAnalyzer.Desktop/Assets/Web/js/validator.js`. Не переносить на Desktop-версию более строгие правила из отдельного прототипа.
*   В `../analyst-pad-prototype/` лежит отдельный статический прототип с похожим названием и отличающимся описанием функций/валидации. Не выдавать его README за точное описание текущей Desktop-версии.
*   Веб-редактор загружает bpmn-js и его стили с CDN. Для работы редактора нужно подключение к интернету; лендинг тоже должен учитывать это, если упоминает онлайн-редактор.
*   GitHub Pages может разместить сам статический лендинг, но не публикует и не запускает Desktop EXE. Не ставь CTA «Скачать приложение», ведущую на несуществующий файл или релиз. Используй ссылку на релиз только если он действительно найден в репозитории/GitHub; иначе оставь легко заменяемый CTA/placeholder и обозначь его в итоговом ответе.

## Рекомендуемое содержание лендинга

1.  **Первый экран:** короткое ценностное предложение: «От BPMN-схемы — к проверенным требованиям и черновику ТЗ». Подзаголовок объясняет, что аналитик рисует процесс, проверяет структуру и получает редактируемую текстовую основу. Основной CTA — посмотреть возможности/пример; CTA скачивания только при наличии реального опубликованного дистрибутива.
2.  **Проблема и решение:** поддержать связь между визуальной схемой процесса и аналитической документацией; не заявлять измеримый эффект без источника.
3.  **Понятный сценарий из трёх шагов:** смоделировать или импортировать BPMN → проверить схему → сформировать и отредактировать документ.
4.  **Карточки функций:** BPMN-редактор, правила проверки, шаблоны документов, проекты на устройстве, экспорт схемы.
5.  **Блок приватности/хранения:** данные проектов сохраняются локально в браузере, облачной синхронизации нет.
6.  **Финальный CTA и футер:** ссылки на репозиторий/релизы только если они доступны; контакты и ссылки не выдумывать.

Визуально можно опираться на текущую тёмную палитру приложения (`#0f1419`, `#1a2332`, синие акценты), но сделать лендинг более просторным и презентационным, с адаптивной мобильной компоновкой. Если в репозитории нет проверенного скриншота или схемы, не выдавай декоративный макет за реальный интерфейс; лучше используй аккуратную иллюстрацию/схематичный пример.

## Требования GitHub Pages

*   Реализация должна быть статической: HTML/CSS/JS и файлы внутри репозитория, без сервера, секретов и обязательного backend.
*   Все ссылки на локальные ресурсы должны работать в корне сайта и в подпапке проектного GitHub Pages (`/<repo>/`): используй относительные пути или корректное вычисление base path, избегай ссылок от `/`.
*   Не добавляй сборщик и зависимости без необходимости; если всё же добавляешь, документируй сборку и настрой Pages на выходную папку.
*   Проверь мобильную ширину, навигацию, доступность ссылок/кнопок и отсутствие битых локальных путей.
*   Подготовь короткие инструкции включения GitHub Pages для выбранного способа публикации.
